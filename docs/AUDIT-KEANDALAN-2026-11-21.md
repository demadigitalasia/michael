## Ringkasan eksekutif

Kualitas kode dan kebersihan keamanan dasar **sudah baik** untuk MVP self-host: scrypt + JWT httpOnly, proxy menutup `/admin/*`, seluruh 11 route admin API memanggil `requireAdmin`, upload memvalidasi magic bytes, route media kebal path traversal, harga selalu dihitung ulang dari DB (bukan percaya klien), sitemap/robots/JSON-LD ada, migrasi mengikuti schema.

Tapi untuk mulai **menerima uang sungguhan**, ada satu tema besar yang belum tertutup: **identitas pemegang hold tidak tercatat, dan fulfillment menganggap semua yang membayar berhak atas batu yang sama.** Dua pembeli bisa sama-sama membuat Stripe session untuk satu batu dan sama-sama dibebankan. Ini dan temuan lain dirinci di bawah.

**Yang paling mendesak sebelum semua itu: commit pekerjaan r4.** Seminggu kerja (fitur baru + perbaikan audit) hidup hanya di working tree.

## Yang terlihat baik dan layak dipertahankan

- **Auth solid untuk MVP**: scrypt + `timingSafeEqual`, JWT httpOnly `secure` cookie, `AUTH_SECRET` fail-fast ≥32 char di production, proxy menutup `/admin/*`, semua 11 route admin API memanggil `requireAdmin` (verifikasi per-route, bukan hanya proxy).
- **Upload & media aman**: magic-byte sniffing menolak MIME palsu, batas 15 MB, nama file acak, route `/media/[...path]` normalize + prefix-check kebal traversal, cache immutable.
- **Harga selalu server-side**: checkout membaca ulang `priceCents` produk dan tarif dari DB — klien tidak pernah menentukan angka.
- **Idempoten webhook** (skip bila sudah PAID), email best-effort tidak menggagalkan fulfillment.
- `x-forwarded-for`-aware rate limit sudah dipakai di login & contact; housekeeping bucket mencegah memory leak.
- Tidak ada `any`, `@ts-ignore`, atau raw SQL; lint + tsc bersih; migrasi sinkron; Dockerfile menjalankan `migrate deploy` sebelum start.
- Sitemap + robots + JSON-LD Product + metadataBase + verifikasi Google dari admin Settings.

## Urutan pengerjaan yang disarankan

1. **Commit sekarang** (P0) — jangan menumpuk P1 di atas tree yang belum aman.
2. **Batch integritas transaksi** (P0/P1 uang): atribusi hold → validasi checkout per-pemegang → webhook transaksional + re-validasi item + jalur refund. Ini syarat minimum sebelum kunci Stripe live.
3. **Token halaman sukses + order number deterministik** (P1 privasi, patch kecil di 2 file + 1 migrasi).
4. **Zona tarif jadi enum** (P1) + **country select** (P2) — satu tema shipping, kerjakan bersama.
5. **Reveal CSS-first** (P1 sisa r4) — satu komponen + regresi visual.
6. **Batch hardening kecil**: RESEND fail-fast, rate limit 3 endpoint, REFUNDED melepas produk, housekeeping cart/order, sitemap, copy status sukses.
7. **Setup test minimal** (unit logika reservasi + 1 integration checkout).
8. **Baru setelah itu**: Stripe live keys + webhook endpoint production, domain Resend, backup Postgres otomatis, monitoring uptime — kesiapan operasional terima uang.

Regresi minimum setelah langkah 2–4: dua browser berebut satu batu (yang checkout & bayar duluan menang, yang kalah harus refund/EXPIRED), cart kedaluwarsa di tengah Stripe checkout, dan matikan JS untuk cek konten tetap terbaca.
